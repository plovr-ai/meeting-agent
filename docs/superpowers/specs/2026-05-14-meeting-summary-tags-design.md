# Meeting Summary Tags Design

## Context

Meeting summaries currently store structured overview, topics, decisions, action items, open questions, risks, and follow-ups in `summary.json`, with a Markdown export in `summary.md`. Knowledge packages are derived from the summary and transcript. The product now needs a small set of post-meeting tags that help users quickly understand a meeting and later support indexing and retrieval.

The tags should be generated by the summary agent, stored structurally, and displayed in the summary UI. They should favor agent insight over a rigid taxonomy: labels may describe meeting type, topic, outcome clarity, execution risk, decision stage, mood, dependency, or another useful dimension chosen by the model.

## Goals

- Generate about 2-4 freeform insight tags during post-meeting summary generation.
- Store tags as structured data in `summary.json`.
- Preserve backward compatibility with existing summaries that do not include tags.
- Display tag chips near the top of the Summary area.
- Show each tag's rationale and confidence on hover.
- Include tags in Markdown summary output for exported review.

## Non-Goals

- Create a fixed taxonomy of meeting types or outcome dimensions.
- Add a tag editing workflow.
- Add transcript evidence navigation from tag chips.
- Mix tags into extracted knowledge facts or judgments.
- Build a full search/indexing UI in this change.

## Data Model

Add a structured summary tag model:

```swift
public struct MeetingSummaryTag: Codable, Equatable {
    public let label: String
    public let rationale: String?
    public let confidence: Double
    public let sourceSegmentIDs: [String]
}
```

Add `tags: [MeetingSummaryTag]` to `MeetingSummary`.

Decoding must use `decodeIfPresent` and default to `[]` so historical `summary.json` files continue to load. Failed summaries should also carry `tags: []`.

The model intentionally does not include a fixed `dimension` field. The label itself is the user-facing insight. `rationale`, `confidence`, and `sourceSegmentIDs` make the output explainable and useful for future indexing.

## Summary Agent Behavior

`OpenRouterMeetingSummaryProvider` should ask the model to return a `tags` array in the JSON payload. Each tag should include:

- `label`: concise natural language, suitable for a chip.
- `rationale`: one short explanation of why the tag applies.
- `confidence`: a number from 0.0 to 1.0.
- `sourceSegmentIDs`: transcript segment IDs supporting the tag.

Prompt guidance should ask for 2-4 tags and explicitly allow mixed dimensions. Useful tags may describe:

- Meeting type, such as `例会`, `市场会议`, `汇报`, `面试`, `播客`.
- Outcome quality, such as `结论清晰`, `方向仍分散`, `行动项较多`.
- Topic or business domain, such as `日本市场进入策略`.
- Risk or dependency, such as `执行依赖法务确认`.
- Decision stage, such as `方案探索`, `已达成初步共识`.

Provider decoding should tolerate missing `tags` by using an empty array, but malformed tag items may fail the provider response the same way malformed decisions or action items do.

## UI

The Summary area should show tag chips near the top of the summary content, before or alongside the overview. The first version should use the chip label as the visible text.

Each chip should expose native macOS hover help using SwiftUI `.help(...)`. Tooltip content should include:

- The tag label.
- The rationale when available.
- Confidence formatted as a percentage.
- Evidence count based on `sourceSegmentIDs.count`.

Example hover text:

```text
市场进入策略讨论
会议围绕日本市场试点、定位和风险展开。
Confidence: 84%
Evidence: 2 segments
```

If `rationale` is missing, the tooltip should still show label, confidence, and evidence count.

The initial UI should not add click behavior, transcript jumping, or a tag details panel. Keeping `sourceSegmentIDs` in the data model leaves room for evidence navigation later.

## Markdown Export

`MeetingSummaryMarkdownRenderer` should include a `Tags` section when tags are present:

```markdown
## Tags

- 市场进入策略讨论 (84%) - 会议围绕日本市场试点、定位和风险展开。
- 结论较清晰 (78%) - 已形成试点范围和后续负责人安排。
```

This keeps exported summaries useful even outside the app.

## Knowledge Package

Do not convert tags into `MeetingKnowledge` facts or judgments in this change. Tags are a meeting-level summary signal, not durable domain knowledge. Future work may add them to meeting markdown frontmatter or a dedicated index, but that should stay separate from the current knowledge extractor.

## Testing

Add or update tests for:

- `MeetingSummary` encodes and decodes tags.
- Legacy summary JSON without tags decodes with `tags == []`.
- `OpenRouterMeetingSummaryProvider` includes `tags` in successful summaries.
- Failed summary generation produces `tags == []`.
- Markdown rendering includes the Tags section.
- Summary UI source/layout includes tag chip rendering and `.help(...)` hover text.

Run `make test` before claiming implementation complete.
