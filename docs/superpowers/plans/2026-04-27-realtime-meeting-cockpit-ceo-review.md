## Baseline Decision

Selected implementation approach: **Caption-first cockpit**.

The product should make live bilingual captions trustworthy before making the goal-intelligence panel feel smart. Customer feedback says users will keep the app open during meetings because language comprehension is the first input problem. Goal tracking and suggested questions only matter if the left-side caption experience is reliable.

## Vision

Build an independent macOS meeting cockpit for cross-border managers:

- 70% live bilingual captions.
- 30% meeting goal state, unresolved issues, and suggested follow-up questions.
- Post-meeting summary derived from transcript plus live meeting progress state.

This is not a browser plugin, not a generic note taker, and not a full meeting-intelligence platform yet.

## Accepted Scope

The implementation plan should include:

1. `MeetingGoal` and `MeetingObjective` models.
2. A pre-meeting goal template:
   - what must be confirmed
   - questions that must be asked
   - owner/deadline/decision expectations
   - lightweight terms/names/projects list
3. `LiveCaptionTurn` and a live caption store that separates:
   - original caption status
   - translated caption status
   - final vs partial text where provider support exists
4. Realtime original captions as the main left-pane experience.
5. Realtime Chinese translation that can lag or fail without blocking original captions.
6. `MeetingProgressAnalyzer` and `MeetingProgressState`.
7. 1-3 low-noise `FollowUpQuestionSuggestion` items.
8. Suggested questions displayed in Chinese and English.
9. One-click copy for the English question.
10. Lightweight health state for captions, translation, and goal analysis.
11. Compact command-center layout tuned for side-by-side use with Zoom, Meet, or Teams.
12. `meeting-progress.json` snapshot artifact.
13. Goal-oriented post-meeting summary using `transcript.json` plus `meeting-progress.json`.
14. Development/test replay path for WAV or transcript fixtures.
15. Dedicated `LiveCaptionStore` as the live meeting state source for UI, translation, analysis, and persistence.
16. Goal analysis trigger policy:
    - run only from final caption segments
    - throttle updates to roughly 30-60 seconds
    - track `lastAnalyzedSegmentID`, `lastAnalyzedAt`, `pendingFinalSegmentCount`, and `lastAnalysisFailure`
17. `meeting-progress.json` should be a versioned snapshot, not an event stream.
18. Live translation should run from final caption segments through a text translation provider and attach translated text to the same `LiveCaptionTurn`.
19. Development replay should use transcript fixtures first, not WAV replay.
20. Meeting progress analysis should start with `MeetingProgressAnalyzing`, `DeterministicMeetingProgressAnalyzer`, and fake analyzers for tests. Real LLM analysis is a follow-up implementation behind the same protocol.
21. Goal-oriented summary should initially produce deterministic JSON/Markdown from `transcript.json` plus `meeting-progress.json`. High-quality LLM-written Chinese management briefs are follow-up scope.

## Not In Scope

- Browser plugin.
- Always-on-top or floating window level management.
- Team/shared terminology knowledge base.
- Automatic terminology learning.
- Realtime speech playback as a product promise.
- Complex provider selection UI.
- Team/cloud/account features.
- SRT/VTT export.
- Historical meeting import as a user-facing workflow.

## State And Persistence Decisions

### Live Caption State

`LiveCaptionStore` is the cockpit source of truth for live caption display and downstream analysis. It should not be folded into `RealtimeTranslationController`.

Minimum turn shape:

```swift
struct LiveCaptionTurn {
    var id: String
    var speaker: TranscriptSpeaker
    var originalText: String
    var translatedText: String?
    var sourceLocale: String
    var targetLocale: String
    var isFinal: Bool
    var captionStatus: LivePipelineHealth
    var translationStatus: LivePipelineHealth
    var sourceSegmentID: String?
}
```

### Analysis Triggering

Goal analysis should run from final segments, with throttling:

```text
new final caption segment arrives
    |
    v
has enough new content?
    |
    v
last analysis was >= 30-60 seconds ago?
    |
    v
MeetingProgressAnalyzer.analyze(...)
```

Do not analyze every token or every partial segment.

### Progress Snapshot

`meeting-progress.json` should be a versioned snapshot:

```json
{
  "schemaVersion": 1,
  "meetingID": "...",
  "goal": {},
  "status": "partiallyAchieved",
  "objectives": [],
  "confirmedItems": [],
  "unresolvedItems": [],
  "suggestedQuestions": [],
  "health": {
    "caption": "live",
    "translation": "delayed",
    "analysis": "updated"
  },
  "updatedAt": "..."
}
```

Do not build an event stream in this phase.

### Analyzer Strategy

Define the protocol now:

```swift
protocol MeetingProgressAnalyzing {
    func analyze(
        goal: MeetingGoal,
        recentCaptions: [LiveCaptionTurn],
        previousState: MeetingProgressState?
    ) async throws -> MeetingProgressState
}
```

This phase should implement deterministic and fake analyzers first. Real LLM analysis should come later behind this protocol.

### Replay Strategy

Build transcript fixture replay first. It should simulate live caption arrival cadence and exercise:

- caption append behavior
- translation pending/succeeded/failed transitions
- analysis throttling
- suggestion refresh behavior
- health state degradation
- long-meeting UI volume

Do not implement WAV realtime replay in this phase.

## Key Review Concerns

1. **Silent failure is the main product risk.**
   Captions, translation, and analysis must each expose independent health state.

2. **Goal analysis must not block captions.**
   The left pane must keep updating even if translation or analysis fails.

3. **The replay path must stay test-only.**
   It is a validation accelerator, not a product import feature.

4. **`meeting-progress.json` needs a versioned schema.**
   Without versioning, future progress-state changes can break old meeting records.

5. **The app needs a real-time throttling policy.**
   Goal analysis should run on a cadence or meaningful transcript boundaries, not every token.

6. **Do not let test replay become a product import feature.**
   Transcript fixture replay is for development and QA only in this phase.

7. **Do not introduce real LLM variability before the state model is stable.**
   A deterministic analyzer is less impressive but much easier to test and debug.
