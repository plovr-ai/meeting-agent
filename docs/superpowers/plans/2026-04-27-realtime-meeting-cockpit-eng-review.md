# Engineering Plan Review: Realtime Meeting Cockpit

Generated by plan-eng-review on 2026-04-27
Branch: main
Status: ACTIVE

## Scope Decision

Selected scope: **A - two-stage implementation, phase 1 core loop only**.

Phase 1 should prove the live meeting cockpit loop without implementing every CEO-review expansion at once:

1. `MeetingGoal` / `MeetingObjective` input model.
2. Dedicated `LiveCaptionStore`.
3. Final transcript segment -> live caption turn.
4. Final caption segment -> text translation -> translated caption attached to the same turn.
5. Caption, translation, and analysis health states.
6. Deterministic `MeetingProgressAnalyzing` implementation.
7. Versioned `meeting-progress.json` snapshot.
8. Basic `LiveMeetingDashboardView` wiring.
9. Transcript fixture replay for development and tests.
10. Deterministic goal-oriented summary from `transcript.json` plus `meeting-progress.json`.

Phase 1 must not become a full meeting-intelligence platform. It is the smallest useful cockpit: users can read original/translated captions live, see whether the meeting goal is progressing, and copy a suggested English follow-up question.

## What Already Exists

- `TranscriptFileWriter` already writes `transcript.txt` and `transcript.json`, including append and replace paths. Reuse this as the durable transcript source instead of creating a second transcript artifact.
- `MeetingStore` already creates per-meeting artifact URLs for audio, transcript, summary, and diagnostics. Extend this artifact registry with `meeting-progress.json`.
- `MeetingRecord` already persists optional artifact URLs with backward-compatible decoding. Add `meetingProgressJSONURL` using the same optional/backfill style.
- `RealtimeTranslationController` already handles realtime speech translation/playback and exposes `LiveTranslationStore`, but it is audio-session oriented. Do not fold cockpit captions into it.
- `OpenRouterTextTranslationProvider` already translates transcript documents and preserves segment IDs. Reuse its provider shape, but add a segment-level live adapter so each final caption can be translated without constructing a full transcript document every time.

## Architecture Findings

### A1. Caption state needs its own source of truth

`RealtimeTranslationController` currently owns speech-translation session state and mutates `LiveTranslationStore` from realtime provider events. It has no original text, speaker, source segment ID, or per-turn translation health. Using it as the cockpit state source would couple the 70% caption experience to optional realtime playback.

Decision: create `LiveCaptionStore` as a separate model/service. Feed it from final `TranscriptSegment` values and let translation/analysis subscribe to the store.

Confidence: 9/10, verified from `RealtimeTranslationController` and `LiveTranslationTurn`.

### A2. Goal analysis must be asynchronous and non-blocking

Captions are the product's primary input. Translation and analysis failures must degrade their own health states without blocking original caption append. The analyzer should run only from final caption segments and be throttled by segment count/time.

Decision: `LiveCaptionStore.appendFinalSegment(...)` should return/update the turn immediately. Translation and progress analysis should run in detached async tasks owned by a coordinator, then publish results back by turn ID / state snapshot.

Confidence: 8/10, based on current async controller patterns and product priority.

### A3. Progress persistence belongs beside meeting artifacts

`meeting-progress.json` is not only UI state; it is the bridge from live cockpit to post-meeting goal summary. It should be registered on `MeetingRecord` and created under the same meeting directory.

Decision: add optional `meetingProgressJSONURL` to `MeetingRecord` and initialize it from `MeetingStore.createMeeting(...)` as `meeting-progress.json`. Decode old metadata with nil and backfill on load if needed.

Confidence: 9/10, verified from `MeetingRecord` and `MeetingStore`.

## Proposed Types

```swift
public struct MeetingGoal: Codable, Equatable, Identifiable {
    public var id: UUID
    public var title: String
    public var objectives: [MeetingObjective]
    public var requiredQuestions: [String]
    public var expectedDecisions: [String]
    public var keyTerms: [MeetingKeyTerm]
}

public struct LiveCaptionTurn: Codable, Equatable, Identifiable {
    public var id: String
    public var sourceSegmentID: String
    public var speaker: TranscriptSpeaker
    public var originalText: String
    public var translatedText: String?
    public var sourceLocale: String
    public var targetLocale: String
    public var isFinal: Bool
    public var captionHealth: LivePipelineHealth
    public var translationHealth: LivePipelineHealth
    public var createdAt: Date
}

public protocol MeetingProgressAnalyzing {
    func analyze(
        goal: MeetingGoal,
        recentCaptions: [LiveCaptionTurn],
        previousState: MeetingProgressState?
    ) async throws -> MeetingProgressState
}
```

Implementation note: keep these in `MeetingAgentCore`, not the app target, so the state machine, persistence, replay, and summary generation can be covered by unit tests.

## Code Quality Review

No blocking code quality issue in the phase 1 architecture after scope reduction.

Two implementation constraints should be explicit:

- Do not migrate the app from `ObservableObject` / `@Published` to Swift Observation in this phase. Apple supports incremental migration, and a broad state-system migration would be unrelated churn.
- Do not put provider-specific logic inside SwiftUI views. Views should consume store/coordinator state and dispatch simple user actions only.

## Failure Modes

- STT produces duplicate or revised final segment IDs: `LiveCaptionStore` must update/dedupe instead of appending duplicate turns.
- Translation provider times out: original caption remains visible; turn translation health becomes degraded/failed.
- Analyzer throws or is slow: previous `MeetingProgressState` remains visible; analysis health degrades; captions continue.
- App closes mid-write: `meeting-progress.json` writes must be atomic, matching existing JSON artifact style.
- Old meeting metadata lacks progress URL: decode succeeds and load can backfill the expected artifact path.
- Replay accidentally becomes user-facing import: keep fixture replay under test/dev entrypoints and avoid adding it to normal app navigation in phase 1.

## Performance Review

Main risk: live UI churn and repeated translation/analysis calls.

Phase 1 constraints:

- Analyze only final caption segments.
- Throttle analysis to roughly 30-60 seconds or enough new final segments, whichever is stricter for early testing.
- Keep a bounded recent-caption window for analyzer input rather than passing the whole meeting every time.
- Translate per final segment, not every partial token.
- Cap visible caption turns in the dashboard or virtualize the list if long-meeting rendering becomes sluggish.
- Persist `meeting-progress.json` only after state changes, with debounce if analysis frequency increases later.

## Not In Scope

- Browser plugin.
- Always-on-top/floating window behavior.
- Full Swift Observation migration.
- Real LLM meeting-progress analyzer.
- High-quality LLM-written Chinese management brief.
- WAV realtime replay.
- Team/shared terminology knowledge base.
- Automatic terminology learning.
- SRT/VTT export.
- Realtime translated speech playback improvements.
- Complex provider selection UI.

## Implementation Order

1. Add models and persistence artifact (`MeetingGoal`, `LiveCaptionTurn`, `MeetingProgressState`, `meetingProgressJSONURL`).
2. Add `LiveCaptionStore` with tests.
3. Add segment-level translation adapter/fake providers with tests.
4. Add deterministic analyzer and progress coordinator with throttling/persistence tests.
5. Add transcript fixture replay for deterministic development/test loops.
6. Add compact dashboard view consuming existing app state plus the new cockpit store.
7. Add deterministic goal-oriented summary from transcript/progress.
8. Run `make test`.

## Handoff Notes

The next implementation Agent should start with tests for `MeetingRecord`, `MeetingStore`, and `LiveCaptionStore`. That creates the durable state boundary first, then the async translation/analysis work can attach to a stable model.

Do not begin by redesigning the whole app shell. The user-validated product promise is live bilingual comprehension plus lightweight goal tracking inside an independent macOS app.
